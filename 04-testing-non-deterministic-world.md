# Testing in a Non-Deterministic World: The Death of Expected Output

*Part 4 of a series on how AI is transforming software engineering — and what it means for architects, developers, testers, and leaders.*

---

The testing discipline was built on a single foundational assumption: given the same input, correct code produces the same output. Write an assertion. Run the test. It passes or it fails. The verdict is binary, reproducible, and authoritative. This assumption is what made automated testing a reliable quality gate.

That assumption no longer holds. And most testing strategies have not caught up.

## The New Failure Mode

When developers write code, they have a mental model of what it should do. Their tests reflect that model. When AI agents generate code, the author often has no mental model at all — or a partial one formed after the fact during review. The tests that accompany AI-generated code are frequently assertions about what the code happens to do, not about what it should do. They pass because the code was written to pass them, not because an independent specification of correctness exists.

The result is a verification system that provides confidence without validity. Green tests become evidence that the code behaves consistently, not that it behaves correctly. Snyk's audit of nearly 4,000 agent skills found that more than a third contained at least one security flaw [1] — not because the code was obviously broken, but because the quality criteria were absent. Developers are generating and shipping code at a volume that overwhelms the capacity for genuine verification, and the testing infrastructure is providing a false sense of safety.

The second failure mode is scale. Test compute requirements grow quadratically with codebase size [2]. AI-assisted development produces more code, more commits, and more agent-driven test runs than human-paced development, and the compounding effect is substantial. ClickHouse, running 20-80 million tests per day across 600 commits and 300 pull requests, had accumulated a backlog of roughly 200 failing test findings per day — a volume no team could investigate manually [3]. At ten times the throughput, the question is no longer whether the tests exist. It is whether the test infrastructure can produce trustworthy evidence fast enough to gate the change rate.

The third failure mode is circularity. When an AI agent generates both code and tests, and another agent reviews the result, the system is checking code against itself. Without an external reference — a human-authored specification, a verified acceptance criterion, a deterministic contract — the review is structurally circular. Both generating and reviewing agents reason from the same training distribution and share the same failure modes. The review provides no independent check [4].

Traditional testing was designed to catch bugs. In an AI-native development environment, the primary quality problem is not bugs in the conventional sense. It is misalignment between what was built and what was intended — and that problem cannot be caught by tests that were generated by the same system that generated the code.

## The Response: Eval-Driven Development

The testing discipline that is emerging for AI-native systems starts from a different premise: you cannot write assertions about the expected output of a non-deterministic system. You can only define acceptance criteria and measure how consistently the system meets them.

This is eval-driven development — a practice where evaluation pipelines replace test suites as the primary quality gate, and where improving those evaluations is the primary engineering activity rather than writing more code.

The architecture of a mature eval system has two layers. The first is capability evals: tasks the agent currently struggles with, evaluated at a low pass rate, that give the team a clear hill to climb. When the team makes architectural improvements — better context, tighter tool definitions, more precise skills — the capability score rises. The second is regression evals: tasks the agent handles reliably, run at a high pass rate, that catch degradation. When a regression score drops, something broke. These two layers work together: as capability evals mature and reach high pass rates, they graduate into the regression suite and the system develops an expanding floor of verified behaviour [5].

The eval harness itself is an architectural investment, not a testing afterthought. It specifies the tasks, defines the acceptance criteria, runs the evaluations consistently, and feeds the results back into the development loop. Without it, changes to prompts, tools, skills, or models are made based on intuition. With it, every change has a measured outcome, and the team has a mechanism for distinguishing genuine improvement from vibe.

The ClickHouse result is the most concrete published evidence of what disciplined eval investment produces. Two months of focused CI investment — approximately 700 pull requests fixing tests and infrastructure — collapsed the failure backlog from 200 findings per day to 3-5 per 10 million test runs [3]. Two autonomous agents now continuously open PRs to address regressions. The assessment from the team: this single use case justifies the entire investment in AI-assisted development. The implication for testing teams is direct: the bottleneck is not the agents or the models. It is the evaluation infrastructure.

Separate loop: regression evals run continuously, alert on drops. The two loops are connected: graduated capability evals become regression evals. Data: 200/day → 3-5 per 10M runs [3].*

## Verifying the Verifiers

When AI generates both code and tests, a deeper problem emerges: who tests the tests?

Mutation testing — deliberately introducing small faults into code and checking whether the existing test suite catches them — addresses this problem directly. It has been known for decades but rarely adopted at scale because generating mutations was expensive and running them was slow. AI changes both sides: AI makes mutation generation cheap, and the urgency is now higher because AI-generated tests need verification more than human-written tests do.

The practical result is sobering. A file with twenty test methods and apparently strong line coverage can score only 70% on mutation testing, with surviving mutants revealing that the tests did not check for required output sections, did not verify behaviour when feature flags were disabled, and did not test boundary conditions at critical thresholds [6]. These are not obscure edge cases. They are the failure modes that cause production incidents. Line coverage is measuring execution, not correctness. Mutation score measures whether the tests can actually catch bugs.

The principle generalises: in an AI-native development environment, metrics that measure activity (lines written, tests executed, PRs merged) systematically diverge from metrics that measure correctness. DORA recognised this and introduced rework rate as a fifth core metric — tracking unplanned fixes pushed to production — specifically because the original four metrics could not capture the quality gap that AI-generated code was creating [7]. Rework rate is a lagging indicator of verification failure. A rising rework rate means the testing infrastructure is not keeping up with the generation rate.

> *Flow: Code → AI introduces mutation → Run test suite → Mutant killed (test is strong) vs mutant survived (test has a gap). Data: 20 test methods, strong line coverage → 70% mutation score, 3 surviving mutants = 3 production incident risks. Contrast with property-based testing: 100% mutation score. Point: line coverage is misleading.*

## Multi-Agent and Statistical Verification

Single-agent verification has a structural ceiling. A single model reasoning about a single diff shares the same training distribution as the model that generated the diff. For simple changes, this is fine. For complex, multi-service, production-grade instrumentation — the kind that actually matters when something breaks — single-model verification fails substantially more often. Benchmark data shows the best available models score around 29% on real-world instrumentation tasks, compared to over 80% on standard coding benchmarks [8]. The gap is not a quirk; it reflects that production verification requires reasoning across multiple system layers simultaneously.

The architectural response is multi-agent cross-validation: separate agents specializing in different dimensions of correctness (telemetry, log patterns, historical change events) reviewing the same change independently and comparing conclusions. This approach has shown 163% improvement in root-cause localization accuracy and 57% improvement in anomaly detection over single-model approaches [8]. The principle is the same one that made code review valuable in the first place: independent perspectives catch different classes of problems.

At sufficient scale, even multi-agent verification runs into a different problem: the test infrastructure itself cannot run reliably enough to make Boolean pass/fail verdicts meaningful. The conjunction of Booleans — all tests pass means ship — breaks down when the test infrastructure has its own reliability distribution and the codebase is large enough that some flakiness is statistically inevitable. Google operates statistical validation at this scale, using probabilistic methods to decide which tests to run and how to interpret their results [2]. For most organizations, this level of scale is still ahead. But the principle is worth understanding now: the appropriate question is not "do all tests pass?" but "what is the probability this change introduces a regression given the available evidence?" That shift from binary to probabilistic thinking is the next evolution of quality engineering.

## What to Build

The practical implications for testing teams follow from this analysis.

**The most important investment is specification before evaluation.** Evals without specs are still circular. The specification — what the system is supposed to do, written in advance of any code — is the independent reference that makes evaluation meaningful. Spec-driven development (Post 3) is not just a developer workflow change; it is a prerequisite for non-circular quality assurance.

**Build capability evals around the tasks that matter, not the tasks that are easy.** Evals over trivial cases provide false confidence. Start with representative samples of real production tasks, define unambiguous acceptance criteria, and build toward a score that means something. The goal is a clear hill to climb — measurable improvement — not a green dashboard.

**Adopt mutation testing for AI-generated test suites.** Line coverage cannot tell you whether AI-generated tests are actually protective. Mutation score can. The investment is justified by the risk: untested tests in an AI-native codebase are a latent reliability problem that compounds silently until it surfaces in production.

**Track rework rate.** If unplanned fixes are rising while commit velocity is also rising, the verification infrastructure is not keeping pace. This is the clearest leading indicator of a quality gap that the development metrics will not reveal.

**Invest in CI infrastructure with the same urgency as AI tooling.** The leverage is there. A well-designed evaluation pipeline compounds: every new agent, every new model, every new architectural change can be validated against the same baseline. The team that invests in this infrastructure now will have a structural quality advantage over teams that treat evaluation as optional.
